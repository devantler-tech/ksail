KSail supports [Amazon Elastic Kubernetes Service (EKS)](https://aws.amazon.com/eks/) as a managed Kubernetes distribution via [eksctl](https://eksctl.io/). A declarative `eks.yaml` (eksctl `ClusterConfig`) defines the cluster shape; KSail provisions it and manages its lifecycle with the same commands used for local clusters.

EKS is the only distribution that uses the [AWS provider](/providers/aws/). It is a cloud distribution — local mirror registries and local registry containers are not supported.

## When to Use EKS

EKS is ideal when you:

- Need a managed AWS Kubernetes cluster with full cloud integrations (ELB, EBS, VPC, IAM OIDC)
- Want to use the same KSail workflow (init → create → update → delete) for cloud clusters
- Require GitOps workflows (Flux or ArgoCD) on managed AWS infrastructure

For local development and testing, consider the [Vanilla](/distributions/vanilla/), [K3s](/distributions/k3s/), or [VCluster](/distributions/vcluster/) distributions instead.

## Prerequisites

1. **AWS account** — with permissions to create EKS clusters, IAM roles, and VPCs
2. **AWS credentials** — configure via `aws configure` or environment variables (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, `AWS_DEFAULT_REGION`)
3. **Docker** — required locally for the `ksail` CLI

## What EKS Provides by Default

| Component      | Status   | Details                                                             |
| -------------- | -------- | ------------------------------------------------------------------- |
| CNI            | Built-in | Amazon VPC CNI (vpc-cni addon)                                      |
| CSI            | Built-in | Amazon EBS CSI Driver addon                                         |
| LoadBalancer   | Built-in | AWS `Service` type `LoadBalancer` support via AWS cloud integration |
| Metrics Server | ❌       | Not provided by default                                             |

## Quick Start

### 1. Initialize an EKS Project

```bash
mkdir my-eks-cluster
cd my-eks-cluster

ksail project init \
  --name eks-default \
  --distribution EKS \
  --provider AWS
```

This generates:
- `ksail.yaml` — KSail cluster configuration
- `eks.yaml` — eksctl `ClusterConfig` (source of truth for cluster metadata)
- `k8s/kustomization.yaml` — directory for Kubernetes manifests

### 2. Review and Edit `eks.yaml`

The scaffolded `eks.yaml` is a minimal starting point:

```yaml
# eksctl cluster configuration.
# See https://eksctl.io/usage/schema/ for the full schema.
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: eks-default
  region: us-east-1
  version: "1.31"

iam:
  withOIDC: true

addons:
  - name: vpc-cni
  - name: kube-proxy
  - name: coredns
  - name: aws-ebs-csi-driver

managedNodeGroups:
  - name: default
    instanceType: t3.medium
    desiredCapacity: 2
    minSize: 1
    maxSize: 3
    volumeSize: 20
    amiFamily: AmazonLinux2023
```

Edit this file to match your AWS environment: region, Kubernetes version, instance types, nodegroup sizing, and addon configuration. Creating a cluster **requires** this file; read-only operations (`list`, `info`) and lifecycle ones (`start`, `stop`, `delete`) work against an existing cluster without it.

### 3. Configure `ksail.yaml`

The `ksail.yaml` references your EKS cluster. All cluster metadata lives in `eks.yaml` — do not duplicate it in `ksail.yaml`:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/devantler-tech/ksail/main/schemas/ksail-config.schema.json
apiVersion: ksail.io/v1alpha1
kind: Cluster
metadata:
  name: eks-default
spec:
  cluster:
    distribution: EKS
    provider: AWS
```

### 4. Create the Cluster

```bash
export AWS_ACCESS_KEY_ID=your-access-key
export AWS_SECRET_ACCESS_KEY=your-secret-key
export AWS_REGION=us-east-1

ksail cluster create
```

KSail invokes eksctl to provision the cluster from `eks.yaml` and waits for completion. See the [AWS provider guide](/providers/aws/) for the full credential and environment-variable reference.

## Lifecycle

| Command                | Effect                                                              |
| ---------------------- | ------------------------------------------------------------------- |
| `ksail cluster create` | Provisions the cluster from `eks.yaml` via eksctl and waits for it  |
| `ksail cluster update` | Updates node-group capacity; optionally upgrades the control plane |
| `ksail cluster delete` | Deletes the cluster, unwinding the eksctl CloudFormation stacks     |
| `ksail cluster stop`   | Scales every managed nodegroup to zero to halt node costs           |
| `ksail cluster start`  | Restores the desired, minimum, and maximum capacity saved by stop   |
| `ksail cluster list`   | Lists clusters in the configured region (all regions when unset)    |
| `ksail cluster info`   | Shows cluster details                                               |

### Experimental control-plane upgrades

To upgrade an ACTIVE EKS control plane from 1.34 to 1.35, set an explicit target
and opt in through `ksail.yaml`:

```yaml
spec:
  cluster:
    distribution: EKS
    kubernetesVersion: "1.35"
    eks:
      experimentalControlPlaneUpgrade: true
```

Preview with `ksail cluster update --dry-run`, then run `ksail cluster update`.
The existing `--kubernetes-version 1.35` flag overrides the YAML target.
`ksail cluster diff --include-version-drift` reports the supported control-plane change
as an in-place update. Without a target, KSail does not discover or select a newer
EKS version. The opt-in is false by default.

Targets may use `1.35`, `v1.35` or the equivalent zero-patch forms. KSail accepts
one forward minor step or an already-current no-op. It rejects skipped minors,
nonzero patch versions, prereleases and rollback requests, including in previews.
The create-time version remains in `eks.yaml`; this target controls updates.

The AWS caller needs `eks:UpdateClusterVersion`, `eks:DescribeUpdate` and the
existing cluster-inspection permissions. KSail verifies immutable cluster
ownership and freezes EKS/STS endpoint and credential selection. It rereads the
cluster identity, ACTIVE status and starting version immediately before submission.
AWS readiness checks remain enabled; KSail does not force an upgrade past them.

KSail waits for the exact AWS update to succeed, then checks that the same cluster
is ACTIVE at the requested version. The wait is capped at 65 minutes and respects
an earlier caller deadline or cancellation. Canceling KSail stops waiting; an
accepted AWS update can continue. Inspect its status before retrying. Once ACTIVE
at the target, another update is a no-op.

This operation changes only the control plane. Upgrade worker nodes and add-ons
separately and check their compatibility; managed node groups must meet AWS's
version prerequisites. KSail does not repair cluster stacks or change remote
network configuration as part of this operation. Concurrent direct AWS operations
are outside KSail's control, and the AWS version API has no conditional
expected-version parameter.

The feature remains experimental pending
[live AWS validation](https://github.com/devantler-tech/ksail/issues/6927).
See [AWS's upgrade guidance](https://docs.aws.amazon.com/eks/latest/userguide/update-cluster.html)
for service prerequisites and rollback operations outside this forward-upgrade path.

### Concurrent lifecycle operations

EKS `start`, `stop`, and `delete` operations from the CLI and the local web/desktop
backend share an operating-system lock for each cluster name in the current user's
KSail state directory. A competing process waits before resolving ownership,
reading capacity snapshots, or changing the cluster. Canceling a CLI command while
it waits leaves the cluster and its saved state unchanged. A second operation in
the same local API service still reports an immediate conflict.

The lock covers the complete operation, including restoration verification and
state cleanup after deletion. AWS account, cluster ARN, and creation-time identity
checks still verify the selected target before mutation. Same-named clusters in
different regions serialize because their local metadata shares a name-scoped
directory; changing a region or credential selector does not bypass the lock.

Lock files remain under `~/.ksail/locks/eks/`, outside the removable cluster state.
The operating system releases the lock when the process exits, including after a
crash. An existing lock file is normal; do not remove it to interrupt an operation.
This coordination applies to processes sharing that local state store. Other
machines, direct AWS operations, `create`, and `update` are outside this lock.

## kubeconfig Context

EKS contexts written by eksctl follow the format `<iam-identity>@<name>.<region>.eksctl.io`. Set `spec.cluster.connection.context` in `ksail.yaml` after cluster creation if you need to override the auto-detected context.

## Limitations

- EKS is a cloud distribution — **local mirror registries and local registry containers are not supported**. Use external registry URLs (e.g., `docker.io=https://registry-1.docker.io`)
- EKS only supports the **AWS provider** — the Docker, Hetzner, and Omni providers are not available
- The control plane keeps running (and billing) while nodegroups are stopped — use `ksail cluster delete` to tear down the cluster and stop its cluster-related charges (resources provisioned by workloads, such as load balancers or persistent volumes, may need separate cleanup)
- `ksail cluster update` applies `desiredCapacity`, `minSize`, and `maxSize` changes to existing managed node groups in-place. Changing an instance type or adding/removing a managed node group requires cluster recreation. Other managed-node-group fields (including AMI family, volumes, labels, taints, subnets, and IAM) are not currently diffed, so update will not detect those changes.
- KSail-managed component installation (CNI/CSI/GitOps/security add-ons beyond eksctl's built-ins) is still in progress — the AWS Load Balancer Controller is available behind the experimental `spec.cluster.eks.experimentalAWSLoadBalancerController` opt-in; see [Support Matrix](/support-matrix/)
